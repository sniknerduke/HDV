2) Core data model you MUST remember (Course/Section/Lesson)
A) courses-service: Course
- Fields: id, code (unique, not blank), title (not blank), price (>0), duration (>0), description, createdBy.
- createdBy dùng để lọc: giáo viên chỉ thấy course của mình; admin thấy tất cả.

B) lesson-service: Section
- Fields: id, courseId, title, description, position (0-based), lessons[]
- One-to-many Section -> Lesson with cascade + orphanRemoval.

C) lesson-service: Lesson
- Fields: id, section (many-to-one), title, type (video/text/quiz), videoUrl, position.

3) Authorization (roles) you should say clearly
- JWT Bearer token; FE axios interceptor auto attach Authorization.
- Backend uses @PreAuthorize:
  - Courses create/update/delete/import-playlist: STAFF | MANAGER | ADMIN
  - Courses list/get: USER | STAFF | MANAGER | ADMIN (public list exists too)
  - Lesson structure read: USER | STAFF | MANAGER | ADMIN
  - Lesson/section mutations: STAFF | MANAGER | ADMIN

10.1 YouTube API import (FE side)
Q1: "YouTube import hoạt động như nào? Dùng endpoint nào của YouTube Data API v3?"
- Answer cues:
   - Key lấy từ env: VITE_YOUTUBE_API_KEY.
   - 2 call chính:
      - GET https://www.googleapis.com/youtube/v3/playlists?part=snippet,contentDetails&id={playlistId}&key={key}
      - GET https://www.googleapis.com/youtube/v3/playlistItems?part=snippet,contentDetails&playlistId={playlistId}&maxResults=50&pageToken=...&key={key}
   - Lấy duration: GET https://www.googleapis.com/youtube/v3/videos?part=contentDetails&id={id1,id2,...}&key={key}
   - Parse ISO8601 duration (PT#H#M#S) -> format hh:mm:ss.

Q2: "Playlist có >50 video thì sao?"
- Answer cues:
   - Code dùng nextPageToken, loop do/while để paginate playlistItems cho đến hết.

Q3: "Nếu quota exceeded / API key invalid thì UX trả về gì?"
- Answer cues:
   - parseYouTubeError map các reason: keyInvalid, accessNotConfigured, dailyLimitExceeded, quotaExceeded, forbidden...
   - UI show toast error; ImportStatus chuyển error.

Q4: "Vì sao cần gọi /videos để lấy duration?"
- Answer cues:
   - playlistItems không có duration; phải gọi videos contentDetails.

Q5: "Vì sao import tạo course status=draft?"
- Answer cues:
   - Giảm rủi ro publish nhầm; cần review thủ công trước khi public.

Q6 (xoáy): "Nếu playlist private/unlisted?"
- Answer cues:
   - Private: API không trả items; code trả 'Playlist not found or is private'.
   - Unlisted: vẫn OK nếu key có quyền và playlist accessible.

Q7 (xoáy): "Tại sao truncate description/title?"
- Answer cues:
   - Tránh vượt giới hạn cột DB (MAX_DESCRIPTION_LENGTH=250, MAX_TITLE_LENGTH=255).


10.2 Gateway Redis Rate Limiter (BE)
Q8: "Rate limit config nằm ở đâu? Quy tắc replenishRate/burstCapacity nghĩa là gì?"
- Answer cues:
   - In api-gateway application.properties: filter=RequestRateLimiter cho routes courses/lessons/payment.
   - replenishRate = số token thêm mỗi giây; burstCapacity = số token tối đa trong bucket.
   - Config hiện tại 1/1 => ~1 req/s per key (khá gắt), burst tối đa 1.

Q9: "Key-resolver dùng cái gì làm key?"
- Answer cues:
   - Bean userKeyResolver trong RateLimiterConfig.java.
   - Lấy header X-User-Id; nếu thiếu -> 'anonymous'.

Q10 (xoáy): "Nếu mọi request không set X-User-Id thì chuyện gì xảy ra?"
- Answer cues:
   - Tất cả share cùng key 'anonymous' => rate limit toàn hệ thống cho anonymous, dễ gây nghẽn.
   - Fix: set X-User-Id tại gateway filter hoặc derive từ JWT subject/IP.

Q11 (xoáy): "Redis đóng vai trò gì trong rate limit?"
- Answer cues:
   - Lưu state token-bucket phân tán (multi-instance gateway). Không dùng in-memory.

Q12: "Tại sao rate limit chỉ bật ở một vài route?"
- Answer cues:
   - Courses/lessons/payment dễ bị spam (scrape, brute force, payment abuse).
   - Orders/cart có thể để riêng tùy policy.

11) Tổng quan kiến thức (REST API structure + SMTP mail + Faker seed)
====================

11.1 Build REST API (Spring Boot/SB) kiểu “chuẩn bài”
- Tư duy layer: Controller (HTTP) -> Service (business) -> Repository (DB) -> Entity/Model.
- Controller:
   - Dùng @RestController + @RequestMapping, mỗi endpoint map sang method.
   - Input: @RequestBody (JSON), @RequestParam, @PathVariable, @RequestHeader.
   - Output: ResponseEntity<T> + HTTP status đúng (200/201/204/400/401/403/404/409/500).
- DTO:
   - Request DTO: chỉ chứa field client được phép gửi (ví dụ LoginRequestDTO).
   - Response DTO: chỉ trả field safe (không trả password/hash).
   - Mapper: convert Entity <-> DTO (ví dụ UserMapper).
- Validation:
   - Dùng @Valid + annotation (NotBlank/Email/Min/Max) ở DTO/entity.
   - Lỗi validation nên trả 400 kèm message.
- Error handling:
   - Có thể gom exception bằng @ControllerAdvice (nếu project có) để trả error format đồng nhất.
- Transaction:
   - Service xử lý write thường đặt @Transactional để đảm bảo atomic.
- Security:
   - “FE chỉ UX”, enforce ở BE: Spring Security + JWT + @PreAuthorize.
   - Mỗi API phải nói rõ role matrix: USER read vs STAFF/MANAGER/ADMIN mutate.

11.2 Cấu trúc file REST API trong project này (nói theo “đúng code đang có”)
- Mỗi microservice thường có các package chính:
   - controller/: nhận request HTTP (ví dụ user-service có UserController, OrderController)
   - service/: business logic (UserService, EmailVerificationService)
   - repository/: Spring Data JPA interfaces
   - model/: entity + enum (User/Order/OrderItem/VerificationCode)
   - dto/: request/response objects
   - config/security/: JWT, filter, CORS, etc (tuỳ service)
- Gateway route /api/* là entrypoint; sau đó forward tới service tương ứng.

11.3 SMTP mail trong user-service (OTP verify) – phải biết để trả lời
Q26: "SMTP mail của dự án build kiểu gì?" 
- Answer cues:
   - Config trong application.properties dùng spring.mail.* (host/port/auth/starttls).
   - Service dùng JavaMailSender + SimpleMailMessage để gửi mail.
   - Flow hiện tại trong EmailVerificationService:
      1) Generate OTP 6 ký tự từ UUID
      2) Save OTP vào DB (VerificationCode)
      3) Send email tới user.getEmail() kèm code
      4) Verify: find user by email -> find code by (user, code) -> enable account -> delete code.

Q27 (xoáy): "Vì sao không nên hard-code password/mail key trong repo?" 
- Answer cues:
   - Lộ credential => bị takeover email/quota.
   - Best practice: dùng env var/secret manager; local dùng App Password (Gmail) hoặc Mailtrap.
   - Nên có rate limit/resend limit cho OTP + expire time (TTL) để chống brute-force.

Q28 (xoáy): "OTP lưu DB vậy có vấn đề gì?" 
- Answer cues:
   - Nên có expiry (createdAt + ttl), max attempts, và có thể lưu hash OTP thay vì plaintext.
   - Cleanup codes cũ (cron) để DB không phình.

11.4 Faker seed data (DatabaseSeeder) trong user-service – nói sao cho chuẩn
Q29: "Seed data dùng gì? chạy khi nào?" 
- Answer cues:
   - Có class DatabaseSeeder implements CommandLineRunner + @Component.
   - Khi app start, Spring gọi run(...) => seeding data demo.
   - Dùng com.github.javafaker.Faker để generate username/email/orders/order_items.
   - Có tạo sẵn account demo: admin/manager/staff (password 123456) + user random.

Q30 (xoáy): "Seed như vậy có rủi ro gì?" 
- Answer cues:
   - Rủi ro: mỗi lần chạy lại TRUNCATE (đang có cleanUpOldData) => mất dữ liệu thật.
   - Nên gate bằng profile/property: chỉ chạy ở dev (spring.profiles.active=dev) hoặc flag ENV.
   - Nếu production: tắt seeder; dùng migration tool (Flyway/Liquibase) thay vì seed tuỳ tiện.
